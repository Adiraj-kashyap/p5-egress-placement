### D-025 · 2026-09-21 · M03 · AWS data transfer and storage read from per-region CSVs; internet base rate
Context: 03_SKILLS S2 says to load AWSDataTransfer/current/index.json (59 MB JSON) and to use the first paid tier "after the first 100 GB free". Both the DT and S3 offers publish a per-region CSV (~0.5 MB and ~0.2 MB) through their own region_index.json, so nothing large needs parsing. In these files the 100 GB free allowance is a separate region-less row (From Region Code empty, price 0, 0-100 GB); the region-specific internet-out tiers start at 0 GB with a price above 0 (us-east-1: 0-10 TB $0.09, then 0.085 / 0.07 / 0.05).
Decision: (1) The pull uses the per-region CSVs and streams them like EC2. (2) A region's DT file also lists rows sent TO that region from every other region, so a row is kept only when its From Region Code is that region (sender pays, D-005) and its To Region Code is another ext region; 8 regions x 7 destinations = 56 pairs. (3) Snapshot rows carry `kind` in {internet, inter_region, internet_free_allowance}; all tiers are kept and nothing is flattened here. (4) The base internet rate for M05 is the internet row with the lowest tier_min_gb and price > 0, which is the region's first tier (a 0-GB start, not 100 GB), while for Azure it starts at 100 GB. The 100 GB free allowance is recorded but not modelled for any provider, which is consistent for all three and slightly overstates internet cost for small volumes. (5) S3 Standard = Product Family Storage, Storage Class General Purpose, Volume Type Standard, usageType ending TimedStorage-ByteHrs (Annotation rows excluded); base rate is the tier with tier_min_gb 0.
Consequence: M05 must flatten AWS internet tiers with the "lowest tier_min_gb, price > 0" rule (identical wording to the Azure rule in D-018).

### D-027 · 2026-09-21 · M04 · N2 core/RAM rates derived from machine-type prices; units GiB
Context: 03_SKILLS S3 wants per-vCPU and per-GiB-RAM rates; the pages publish per-machine-type hourly prices.
Decision: per region, least-squares fit of price = vCPU x core + GiB x ram over all 29 N2 predefined types (standard, highmem, highcpu), on-demand hourly column only. The fit residual is recorded per row and must be <= 1e-5 USD/h. In the live pull it is 0 in all 8 regions, so the prices are exactly linear (us-central1/us-west1 give 0.031611 / 0.004237, the familiar SKU rates). The pages quote network and storage per GiB (2^30 B); rows keep usd_per_gib and add usd_per_gb = usd_per_gib / 1.073741824 (01_CONVENTIONS S3 unit). RAM rates stay per GiB-hour, because shapes are specified in GiB on all providers.
Consequence: M05 composes n2-standard-{2,4,8,16} as vcpu x core + ram_gib x ram, and must use usd_per_gb / usd_per_gb_month for egress and storage.

### D-042 · 2026-09-22 · M10 · ILP implementation choices
Context: §S6 gives the model; several details are left open.
Decision: (1) x[c,l] exists only for allowed locations, so pins remove variables rather than adding x = 0 rows. (2) Both directions of an edge share one y-set with coefficient w_uv·p[l,m] + w_vu·p[m,l]; self-loops (u = v) cost w·p[l,l] and are folded into the linear x cost. (3) Both formulations create all |P|·|L|² continuous y ≥ 0. McCormick keeps only the lower bound y ≥ x_u + x_v − 1, because the objective is minimised and every merged coefficient is ≥ 0 (build_model raises otherwise). PuLP 3.3.2 warns that PULP_CBC_CMD will be removed in PuLP 4.0. (5) Proven optimality, best bound and gap come from the CBC log (`placement/cbc_log.py`). A real 3 s time-limited run showed PuLP reporting `Optimal` while CBC said `Stopped on time limit` (gap 2.89). That log tail is kept as `tests/data/cbc_stopped_on_time.log`. (6) runtime_s = wall time around the CBC call. Model build time is recorded separately as build_s, and CBC's own wall time as cbc_wall_s. (7) Brute-force tests use 20 seeded random tiny instances built in the test file. These are test inputs, never reported. T1 on core (12^4 = 20,736 assignments) is also enumerated against real prices.

### D-044 · 2026-09-22 · M11 · Greedy order, tie-breaking and 1-opt rules
Context: §S7 says order by total incident traffic and place each component at its cheapest location given placed neighbours; the module asks for deterministic tie-breaking by location id. D-039 shows aws:us-east-1 and azure:eastus compute prices tie exactly, so ties are real, and float sums can differ in the last bits.
Decision: (1) "Incident traffic" = inter-component GB in + out (self-loop counted once); internet GB is excluded because it does not couple components. Equal totals keep topology order (stable sort). (2) Candidate location costs within a relative 1e-9 of the minimum count as tied; the lexicographically smallest location id wins (so aws < azure < gcp). (3) 1-opt: each pass visits components in the same order and moves a component to its best location if that lowers its local cost by more than the same relative 1e-9 (prevents float cycling); stop after a pass with no move or at max_passes=50. (4) Deltas are computed incrementally from incident edges (`local_cost`), and a test checks them against `evaluate`; reported costs always come from `evaluate`.
Consequence: on exact aws/azure ties the greedy prefers aws, the same as B1's first tie-break. This can make greedy look worse than B2-best on instances where the tie is broken by storage/egress later; 1-opt can repair single-component cases only.

### D-046 · 2026-09-22 · M12 · SA stale rule = "frozen" (no best improvement AND no accepted downhill move)
Context: §S7 says stop "at T < 1e-4·T0 or no improvement in 20 temperature steps". Read literally (best cost did not improve), SA started from greedy stops after exactly 20 steps, because T0 is calibrated so ~80% of uphill moves are accepted and the best is the greedy start. With alpha=0.995, 20 steps only cool to 0.995^20 = 0.905·T0. Probe on T1-T3 core, seed 0: literal rule stops at T = 0.905·T0 and returns greedy unchanged (483.57 / 1,028.79 / 1,822.60); the frozen rule reaches the ILP optimum on all three (481.18 / 1,028.79 / 1,789.88), stopping at T/T0 = 0.014 / 0.0016 / 0.0008. Decision: a temperature step counts as stale only if the best did not improve AND no strictly downhill move (delta < -1e-9 relative) was accepted in that step. This is the standard "frozen" criterion (the search sits in a local minimum and only rejects or makes zero-cost moves). 20 consecutive stale steps stop the run; T < 1e-4·T0 is kept as the hard stop. The literal rule stays available as `stale_rule="best"`. Other §S7 choices: T0 by bisection so the mean of exp(-d/T0) over the uphill deltas of a 200-move probe from the start state is 0.8 (fallback T0 = 1e-9 relative when the probe sees no uphill move); moves_per_temp = n·|L|; relocation p=0.8, swap p=0.2 (a swap draw that is invalid, same location or not allowed, falls back to a relocation); the trace has one point per temperature step. The rule was chosen for the reason above, before the 10-seed run; it was not tuned to the benchmark.
Consequence: SA runs to a frozen state (about 1-2 s on T3). With `time_limit` set, results are no longer seed-deterministic; the M12 runs use no time limit.
